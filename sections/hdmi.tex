\subsection{HDMI Output Protocol}

% The default PYNQ video overlay routes every pixel through DDR3. The PS
% writes a complete frame into SDRAM, a VDMA engine reads it back over
% the AXI bus, and the VTC clocks it through AXI4-Stream to Video Out
% and RGB-to-DVI to the display. Buffering a full 480p frame costs
% $640 \times 480 \times 3 = \mathbf{900\,\text{kB}}$ of SDRAM per
% frame, and at 60\,fps the VDMA alone consumes $\mathbf{54\,\text{MB/s}}$

% A general-purpose game engine must allow any PL rendering block to
% drive the display directly, without PS involvement or memory
% allocation. The VDMA breaks this in two ways. First, frame rate
% becomes coupled to PS scheduling: network interrupts, game logic, and
% Python overhead all compete with the DMA transfer, producing variable
% frame timing. Second, the display can scan out a frame while the PS is
% still writing the next one into the same buffer, causing tearing where
% the top and bottom halves of the screen show different frames. Neither
% is acceptable in a real-time multiplayer context.

% The VDMA is removed entirely. The raycaster AXI-Stream output is
% connected directly into \texttt{v\_axi4s\_vid\_out\_0}, with the VTC
% and RGB-to-DVI IP retained. Figure~\ref{fig:hdmi-compare} shows the
% two pipelines side by side. The key insight is that the VTC is a
% hardware counter driven by a fixed pixel clock: it is physically
% incapable of producing an inconsistent frame rate regardless of what
% the PS is doing. There is no shared framebuffer, so there is no
% surface for tearing to occur on. Any future rendering block, whether a
% sprite engine, a tile renderer, or a different 3D algorithm, can be
% substituted into the same pipeline and drive the display without
% modifying the PS at all.

The default PYNQ video overlay routes every pixel through DDR3: the PS
writes a complete frame into SDRAM, a VDMA engine reads it back over AXI,
and the VTC clocks it through AXI4-Stream to Video Out and RGB-to-DVI.
Buffering a full 480p frame costs $640 \times 480 \times 3 =
\mathbf{900\,\text{kB}}$ per frame; at 60\,fps the VDMA alone consumes
$\mathbf{54\,\text{MB/s}}$ of AXI bandwidth.

This introduces two problems in a real-time multiplayer context. Frame
rate becomes coupled to PS scheduling, where network interrupts, game
logic, and Python overhead compete with the DMA transfer. The display can
also scan out a frame while the PS is still writing the next one into the
same buffer, causing tearing.

Both are eliminated by removing the VDMA entirely and connecting the
raycaster AXI-Stream output directly into \texttt{v\_axi4s\_vid\_out\_0},
retaining only the VTC and RGB-to-DVI IP. Since the VTC is a hardware
counter driven by a fixed pixel clock, frame rate is decoupled from PS
activity entirely. With no shared framebuffer, tearing has no surface to
occur on. Figure~\ref{fig:hdmi-compare} shows the two pipelines.

\paragraph{Benefits and resource cost:}
End-to-end pixel latency falls from $\mathbf{16.7\,\text{ms}}$ to under
$\mathbf{1\,\mu\text{s}}$, and the 54\,MB/s AXI bandwidth is fully
recovered for PS network and game-state threads. Frame rate is
hardware-locked to the VTC pixel clock, eliminating stuttering and
tearing, while the ARM core is reduced to writing a single game-state
packet to BRAM each tick. The saving is in bandwidth and PS cycles rather
than PL fabric: the retained VTC, AXI4S-to-Video-Out, and RGB-to-DVI IPs
occupy approximately 1,800\,LUTs and zero BRAM tiles.
