The Digital Differential Analysis (DDA) algorithm's repetitive per-column computation and fixed-point arithmetic lend themselves naturally to hardware implementation in the PL, where such operations can be executed far more efficiently than on a general-purpose CPU.

The BRAM controller exposes an AXI interface to the PS, through which the map layout, player coordinates, and camera angle are written each game tick and consumed by the PL for rendering. The raycasting engine uses player position, angle and map data stored in the shared BRAM, to then run the DDA algorithm to find the distance to the closest wall. For each vertical screen column, a ray is cast from the player's position in the direction determined by the camera plane. 

\vspace{0.5em}

As shown in Figure~\ref{fig:ray-miss}, stepping along the ray at fixed increments risks skipping over walls. Instead, DDA jumps from one grid boundary to the next by computing the distance to the nearest horizontal and vertical tile edge, advancing to the closer edge and repeating the process until it reaching a wall (Figure~\ref{fig:ray-hit}).

    \centering

    \caption{Non-DDA Ray Projection}
    \label{fig:ray-miss}
\end{figure}

\begin{figure}[H]

    \includegraphics[width=0.5\linewidth]{images/ddaWallHit.png}
    \caption{DDA Ray Projection}
    \label{fig:ray-hit}

\vspace{0.5em}

Once a wall tile is detected, the perpendicular distance of the wall to the camera plane is calculated using the formula:
\[perpWallDist = (sideDistx - deltaDistX)\]
this is illustrated in Figure~\ref{fig:dist-calc}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.5\linewidth]{images/distancecalc.png}
    \caption{Perpendicular Distance Calculation}
    \label{fig:dist-calc}
\end{figure}

With $perpWallDist$, the column height $L$ on the screen is calculated using the formula:
\[L = h/perpWallDist\]
Where $h$ is the height of the screen in pixels (240).

More distant walls produce shorter columns — naturally encoding perspective.

\subsubsection{How the raycaster is controlled}
The raycaster needs 4 things from the PS to render a specific image.
\begin{itemize}
    \item 32x32 map, stored in the first 32 addresses of the BRAM as 32 bit words, where each bit represents a 'walled' cell (1), or an open cell (0).
    \item In the next address the player's coordinates within the 32x32 bit map are held, with the X coord the most significant 16 bits, and the y coord the leats significant 16 bits (both in Q6.10 format).
    \item Next address stores the angle the player is facing in the least significant 12 bits, where this 12 bit angle value maps to a full rotation - this is a particularly easy way of doing angles as the wraparound nature of addition correctly expresses the wrap around nature of the angles.
    \item Next address stores prite coordinates (usually representing the other player) once again x coords in the most significant 16 and y coords in the least significant.
\end{itemize}


\subsubsection{Implementation in hardware}
The general process was mapping the C++ software raycaster provided in \href{https://lodev.org/cgtutor/raycasting.html}{this online graphics guide}, into digital logic using verilog. To do this i developed my \href{https://lucid.app/lucidchart/b7ab8f69-34e7-4cf8-9b9b-f49715732eff/edit?viewport_loc=-2031%2C-77%2C6192%2C3343%2CYexzRyfn2-1H&invitationId=inv_7309e510-de33-44a8-bcfb-b6b6e7498bd5}{own flowchart} of the raycasting algorithm and converted sections into verilog.
The main difficulty of this was the arithmetic in the DDA raycasting algorithm. We wanted to engineer it for:
\begin{itemize}
    \item Low Latency
    \item Low resource utilisation
    \item Low power
    \item Parallelism
    \item Precision
\end{itemize}
To best leverage the FPGA's resources custom fixed point arithmetic was used, this was effective as it could be done combinationally and to an acceptable precision. Of course with fixed point there is a limit in precision, we therefore specially selected fixed point representations for different values, customising them so to give them the finest resolution, in the ranges they could physically represent, we kept bit widths at 16 bits to minimise multiplier + adder usage where necessary. 
For example:
\begin{itemize}
    \item Unsigned Q6.10 for distances and coordinates. In the 32x32 map the max distance (corner to corner) is approx. 45 the 6 integer bits can represent this magnitude, but also have 10 bits of fractional precision.
    \item Direction Vectors : Two's compliment Q2.14. When representing the direction the viewer is facing we intepret it as a unit vector, a unit vector we must find the x component and y component of. These components can be between -1 and 1, and need high precision to accuratelt represent the direction of the unit vector.
\end{itemize}

For more complex functions such as $sin(x)$, $cos(x)$ and divisions (to find column height or the $1/|dirx|$)- which are particularly difficult to do fast with minimal resources in digital logic, we had to find better ways to maximise speed and minimise latency, without a noticeable worsening of precision.

For these functions we settles on using LUTs, we chose these for a few reasons:
\begin{itemize}
    \item Low latency, can also pipeline, we wanted to make sure the raycaster didnt limit frame-rate
    \item Mapped into BRAM or LUTS, at this stage in the project we wanted to minimise DSP usage and general resource utilisation to leave space for new features as the raycaster develops.
    \item Luts mean you can pick your precision on both ends we spent time calculating how much precision we would need for the input and outputs and their uses down the line, so that we could minimise the sizes of the LUTS.
\end{itemize}
These LUTs would be generates as .mem files using python scripts and would then be loaded into arrays in verilog using the \texttt{$readmemh} instruction.

\subsubsection{AXI Video stream output block \& pixel generation}

Whenever the distance of a ray is calculated it indexes the 240/distance LUT to find how tall the wall in the corresponding column should be, a pulse is sent to the hdmi pixel gen block so that knows to store this height in its array of column heights.

In the next frame the hdmi pixel gen block copies these values into its 'current heights' array, then as it is generating outputing pixels, we keep a track of the x and y coordinates of the current pixel. Which we can then use determine which column on the screen we are in - how tall the wall is here, whether we are in the wall, above it, or below it which we can then use to decide which pixel to output.

We also coded the hdmi pixel gen block to handles all the AXI signals for this video data stream: 
\begin{itemize}
    \item TDATA
    \item DVALID
    \item TUSER
    \item TLAST
    \item TREADY
\end{itemize}




\subsection{Extension 1: Sprite Rendering}

Fully customiseable sprite and texture loading, can change the relevant .mem files containing the sprite bitmap to renderdifferent sprites/wall textures.


\begin{enumerate}
    \item During wall raycasting, record the perpendicular distance of each vertical stripe in a 1D Z-buffer.
    \item Project each sprite onto the camera plane by subtracting the player position from the sprite position, then multiplying by the inverse of the 2$\times$2 camera matrix.
    \item Determine the on-screen size of the sprite in both axes using its perpendicular distance.
    \item Render the sprite column by column, skipping any column whose depth exceeds the corresponding Z-buffer entry from the wall pass.
    \item Within each column, render pixel by pixel using a transparent colour key, ensuring sprites are not drawn as solid rectangles.
\end{enumerate}

The sprite casting happens in parallel as the raycasting (taking significantly more time). It therefore has more time and uses multi-cycle dividers for the camera transformations.

The sprites are stored as 16x16 12 bit rgb bit maps, they also have invisible pixels where the raycaster will instead display the pixels from the wall/floor/ceiling behind, meaning different shaped sprites can be rendered.

\subsection{Extension 2 : Texture Rendering}
The textured raycaster shares the same core logic as the untextured version, with a key additions: 
when in a wall it must know both its position in the y and x direction on that wall to then sample the correct part of the texture map.

The Xposition in the wall can be saved at the end of the DDA stepping, the y position requires a division to calculate how far through the walls column you are, and hence which rgb pixel to sample.

The bitmaps are 32x32 12bit (to save area) rgb which is then 0-extended to 24bit rgb pixels.




\subsection{Testing}
Testing was done throughout the development of the raycaster - important modules had testbenches developed to assess them.

Another very useful testing strategy was the testbench for the whole raycaster, which when simulating could store pixel data into a file, which a python script could then reshape into 640x480 PNG files. This was a very effective way of testing as it visualised issues clearly, and was significantly quicker than running bitstreams, and didnt require any periphers (eg monitor).

For more complicated testing relating to bugs in arithmetic, viewer wires/outputs would be made on the module so that we could observe different variables values through time on the waveform, this wnabled rapid identification of issues. This is why you will also see loads of \textit{'v\_'} wires on the raycaster modules, they indicate viewer wires, they have been left as when unconnected vivado simply removes them in its optimisation step.






\subsection{Assessment}

There are three key areas to assess the raycasters performance:

\begin{itemize}
    \item Speed : ~\ref{fig:speed}
    The raycaster performs raycasting for the next frame whilst the current frame is being output. When running the raycaster easily manages 60fps, resulting in smooth motion. As you can see from the frame and ray\_done signals in Figure ~\ref{fig:speed}, the raycaster has completed the dda algorithm for all rays of the next frame in about 1/12 the time it takes the frame to be output. This means the hdmi is the bottleneck, not the renderer, and that theoretically, if the hdmi and monitor were modified, the raycaster could support frame-rates up to and abive 600fps.
    \item Utilisation --- see Figure~\ref{fig:util}
    Due to the nature of this project and the options to add new features, we sought to minimise resource utilisation wherever we could - to make the leanest, fastest renderer, and leave space for extra features. In the end, the \textbf{whole system} on the PL, including AXI drivers, BRAM controllers etc : summed up to a utilisation of approximately 20\%, this is a testiment to how we developed our own optimised, custom ip blocks.
    \item Image Quality --- see Figure~\ref{fig:neon}, Figure~\ref{fig:early}, Figure~\ref{fig:sprite}
    The walls are rendered correctly to look 3D, with no fisheye, and no inconsistencies/breakdowns. 2D 16x16 sprite bitmaps are correctly rendered with occlusions with walls correct. 32x32 wall textures are also correctly rendered.
\end{itemize}
